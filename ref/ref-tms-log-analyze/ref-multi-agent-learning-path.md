# 멀티에이전트 오케스트레이션 학습 경로

> 목적: 로그 초도 분석 AI를 구현하기 위해, **왜 이 구조가 나왔는지**를 흐름으로 이해하고  
> 무엇을 더 알아야 하는지 파악한다.

---

## 1. 흐름: 왜 이 구조가 나왔는가

### Step 1. LLM 하나로 복잡한 일을 시키면 왜 안 되나?

LLM은 텍스트를 잘 생성하지만, **실제 시스템과 상호작용하지 못한다.**

- 로그 파일을 직접 읽지 못함
- SSH로 서버에 접속하지 못함
- DB에서 유사 케이스를 조회하지 못함

→ 그래서 **Tool Use** 개념이 나왔다.  
LLM이 "이 함수를 실행해줘"라고 요청하면, 외부 코드가 실행하고 결과를 돌려주는 방식.

---

### Step 2. Tool Use만으로는 왜 부족한가?

Tool을 쓸 수 있게 됐지만, **어떤 순서로, 왜 그 Tool을 써야 하는지** LLM이 판단하지 못했다.

- 결과를 보고 다음 Tool을 결정하는 **추론 과정** 이 없음
- 한 번 Tool을 쓰고 끝 → 중간 결과를 반영 못 함

→ 그래서 **ReAct 패턴** 이 나왔다.  
`Reason(추론) → Act(도구 실행) → Observe(결과 확인) → Reason → ...`  
이 루프를 반복하면서 점진적으로 답에 도달한다.

**우리 프로젝트에서:** `root_cause_analyzer`가 SSH 조회 → 결과 분석 → 추가 조회 반복하는 것이 바로 ReAct.

---

### Step 3. ReAct 하나만으로는 왜 부족한가?

ReAct 에이전트 하나가 모든 걸 하면:

- 로그 수집 + 지식 검색 + 원인 분석 + 보고서 작성을 **한 LLM이 다 기억** 해야 함
- Context가 너무 길어져서 판단 품질이 떨어짐
- 역할이 섞여서 각 단계의 책임이 불명확해짐

→ 그래서 **멀티에이전트** 가 나왔다.  
역할을 나눠 각 에이전트가 자기 일만 집중한다.

**우리 프로젝트에서:** collection / knowledge_retriever / root_cause_analyzer / report_generator로 역할 분리.

---

### Step 4. 멀티에이전트를 어떻게 조율하나?

에이전트들이 각자 일하면, **누가 다음에 누구를 불러야 하는지** 결정하는 주체가 필요하다.

방법 1 — **고정 파이프라인:** A → B → C 순서 고정 (단순하지만 유연성 없음)  
방법 2 — **supervisor 패턴:** 중앙 LLM이 상황 보고 다음 에이전트 결정 (유연하지만 복잡)

→ 우리는 supervisor 패턴을 선택했다.  
supervisor가 매 단계 결과를 보고 `{ "next": "root_cause_analyzer" }` 같이 라우팅.

---

### Step 5. 그래서 지금 우리가 모르는 것

이 흐름은 이해했지만, 실제 구현에서 결정해야 할 것들이 남아 있다:

| 결정 사항           | 모르는 것                                              |
| ------------------- | ------------------------------------------------------ |
| supervisor 프롬프트 | 어떤 기준으로 다음 에이전트를 고르게 할 것인가         |
| loop 종료           | 언제 분석이 끝났다고 판단하나 (LLM 판단 vs 규칙)       |
| 실패 처리           | sub-agent가 실패하면 supervisor가 어떻게 반응해야 하나 |
| 평가 기준           | 분석 결과가 좋은지 나쁜지 어떻게 측정하나              |
| 비용/속도           | 한 번 분석에 얼마나 걸리고 얼마나 드나                 |
